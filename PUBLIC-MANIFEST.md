# PUBLIC MANIFEST — what belongs on kilokaki.com

**Owner:** Nori (content). **Consumer:** `scripts/deploy.sh` (Mochi).
**Written:** 2026-07-17. **Status:** allow-list spec. Not yet enforced by the deploy.

## Why this file exists

`deploy.sh` ships `SRC_DIR` to the public web root. Nobody ever defined what
`SRC_DIR` is *for*, so it became "the repo" — and the repo is a working tree,
not a website. Consequence, live on prod right now: 9 build scripts and an
internal copy deck, all serving 200.

An exclude-list can't fix this. Every new non-public file added to the repo
ships by default and someone has to notice. **The default must be "does not
ship."** This is the allow-list. If it isn't listed here, it isn't public.

## ⚠️ For Mochi — `--exclude` will NOT clean this up

`scripts/deploy.sh` already carries `--exclude='scripts/'`. **That does not
remove the 9 live `.py` files, and it will look like it did.**

rsync `--exclude` **protects** a path from `--delete`. It means "ignore this on
both sides" — so the live copies become invisible to the deploy rather than
removed. They stay 200 forever and every future dry-run reports clean. That's a
false PASS with a long fuse, written into the tooling.

Removal needs **one of**:
- a one-time manual `rm` on prod (then the exclude keeps them from returning), or
- `--delete-excluded` on a single deliberate run (**dangerous** — it deletes
  *everything* excluded, including anything intentionally prod-only; do not make
  this permanent), or
- better: build the rsync source from **this manifest** instead of from `SRC_DIR`,
  so the allow-list is the deploy's actual input and the question stops recurring.

The third option is the durable one. The first two just move the problem.

## Maintenance

Adding a new public page or asset means **adding it here**. If this file rots,
the deploy silently reverts to shipping the working tree — which is exactly the
failure it exists to prevent.
